# AstroNeko → CNYOS: เส้นทางบริการและคำสั่งซื้อ

วันที่: 5 กันยายน 2026

สถานะ: ข้อกำหนดเป้าหมายจากเจ้าของและผลตรวจ source; ยังไม่ใช่ flow ที่เชื่อมใช้งานจริงครบวงจร การเพิ่มเอกสารนี้ไม่เปิดฟีเจอร์ ไม่เปลี่ยนการชำระเงิน และไม่เปลี่ยนฐานข้อมูล

## เส้นทางเป้าหมาย

AstroNeko → ผู้สนใจ → ตรวจความเหมาะสม/ยืนยันตัวตน/เลือกคิว → ชำระค่าปรึกษา → CNYOS telemedicine และ OPD → ผู้ประกอบวิชาชีพยืนยันแผน/ใบสั่งยา → ห้องยาตรวจและสอบถามเพิ่มเติม → ยืนยันราคาและชำระค่ายา/ผลิตภัณฑ์ → หยิบสินค้าพร้อมจำหน่าย หรือผลิตและผ่าน QC → ตรวจจ่าย → แพ็ก/จัดส่ง → ยืนยันรับ → ติดตามผลและบริการหลังการขาย

AstroNeko เป็นช่องทางสร้างความสนใจและส่งต่อเข้ารับบริการ ผลด้านโหราศาสตร์หรือธาตุจากกิจกรรมการตลาดไม่สร้าง diagnosis, prescription หรือ production order โดยอัตโนมัติ ผู้ประกอบวิชาชีพต้องประเมินและยืนยันข้อมูลทางคลินิกอย่างเป็นอิสระ

| ขั้น | ผู้รับผิดชอบ | ผลส่งต่องาน/เงื่อนไข |
|---|---|---|
| 1. AstroNeko lead | การตลาด | ที่มาของแคมเปญ รหัสส่งต่อ ความสนใจ และช่องทางติดต่อที่ยินยอม |
| 2. Intake และเลือกคิว | ผู้รับบริการ/เจ้าหน้าที่คลินิก | ตรวจความเหมาะสมสำหรับทางไกล ยืนยันตัวตนและความยินยอมก่อนเชื่อมข้อมูลคลินิก; ล็อกคิวชั่วคราวก่อนรับเงินเพื่อไม่ขายเกินกำลัง |
| 3. ชำระค่าปรึกษา | ผู้รับบริการ/ระบบชำระเงิน | ใบสั่งบริการค่าปรึกษา; สถานะ paid ต้องมาจากหลักฐานฝั่งผู้ให้บริการชำระเงินที่ตรวจสอบแล้ว ไม่ใช่หน้า success ใน browser |
| 4. Telemed + OPD | ผู้ประกอบวิชาชีพตามสิทธิ์ | คิวปรึกษาและ encounter ผูก HN; บันทึกประวัติ/ประเมิน/แผน/ใบสั่งยา; มีเส้นทางส่งต่อหากไม่เหมาะกับทางไกล |
| 5. Pharmacy review/inquiries | ห้องยา | ตรวจใบสั่งยา ความครบถ้วน วัตถุดิบ/สต็อกและราคา; หากต้องแก้ใบสั่งยาส่งกลับผู้สั่งและเก็บ revision ไม่แก้แทนโดยเงียบ |
| 6. ชำระค่ายา/ผลิตภัณฑ์ | ผู้รับบริการ/การเงิน | ใบเสนอราคาที่ผูกกับใบสั่งยารุ่นที่อนุมัติ รวมค่าจัดส่ง; ไม่บังคับว่าทุก consultation ต้องซื้อยา |
| 7A. มีสินค้าพร้อม | ห้องยา/คลัง | จองและหยิบ lot ที่ผ่าน release โดยใช้หลัก FEFO; กันออร์เดอร์ซ้ำและแย่งสต็อก |
| 7B. ต้องผลิต | ฝ่ายผลิต/ผู้ตรวจคุณภาพ | Production request → ออกใบผลิต → เบิกวัตถุดิบ → batch → independent QC → finished-goods lot |
| 8. ตรวจจ่าย/แพ็ก/ส่ง | ห้องยาและคลัง/ขนส่ง | ตรวจรายการ จำนวน lot ฉลากและผู้รับ; shipment/tracking ผูก order; ของที่ไม่ผ่าน QC ไม่เข้าสถานะพร้อมส่ง |
| 9. CRM และ feedback | บริการลูกค้า/ผู้ประกอบวิชาชีพ | แยกเรื่องพัสดุ/บริการออกจากผลทางคลินิก; อาการผิดปกติต้องส่งคิวทบทวน ไม่เข้า campaign ขายซ้ำอัตโนมัติ |

### การแบ่งการชำระเงิน

ค่า consult และค่าสินค้าเป็นคนละภาระส่งมอบ จึงควรมีรายการและสถานะแยกกัน แม้ต่อไปจะเสนอแพ็กเกจรับเงินก้อนเดียว การยกเลิก คืนเงิน ขาดนัด ไม่สามารถให้บริการ การแก้ราคา และชำระเกินต้องมีนโยบายที่คลินิกยืนยันและมีรายการตรวจสอบย้อนหลัง

การรับเงินก่อน consult/ผลิตเป็นข้อเสนอออกแบบธุรกิจ ไม่ใช่ข้อสรุปว่ากฎหมายบังคับจ่ายสองครั้ง ต้องตรวจเงื่อนไขบริการ สัญญา และการชำระเงินก่อนเปิดขาย

### สิทธิ์และการส่งข้อมูล

- แต่ละคลินิกคง database/credentials แยกตามข้อกำหนดเดิม ห้ามโยกข้อมูลข้ามคลินิกด้วย lead/referral เดียวกันโดยปริยาย
- ฝั่งการตลาดใช้ข้อมูลติดต่อที่ได้รับอนุญาตและสถานะ conversion ที่จำเป็น; ไม่รับ OPD รายการยา หรือ feedback สุขภาพเพื่อใช้โฆษณาโดยปริยาย
- คลังเห็นรายการแพ็ก ผู้รับ ที่อยู่และข้อมูลที่จำเป็นต่อการส่งมอบ; ไม่ได้สิทธิ์เปิด OPD ทั้งฉบับ
- การยินยอมรับบริการและการยินยอมการตลาดเป็นคนละวัตถุประสงค์ ไม่บังคับรับการตลาดเพื่อรักษา
- ใบสั่งบริการ ใบชำระเงิน appointment, encounter, prescription revision, production batch, shipment และ follow-up ต้องอ้างอิงกันภายใน tenant; ใช้รหัสสาธารณะที่ไม่เปิดเผยข้อมูลสุขภาพกับระบบภายนอก
- การจอง จ่ายเงิน ผลิตและส่งสินค้าต้องมีการป้องกันการทำซ้ำและตรวจสถานะปัจจุบันก่อนเปลี่ยนงาน การระงับ subscription ต้องห้ามเริ่มงานคลินิก/ผลิต/จัดส่งใหม่ แต่การรับหลักฐานทางการเงินจาก provider ที่เกิดไปแล้วต้องมีทางกระทบยอดที่จำกัดสิทธิ์และไม่ปลดระงับเอง

## สิ่งที่มีใน source และสิ่งที่ยังต้องต่อ

| ส่วน | หลักฐานใน source | ข้อจำกัด |
|---|---|---|
| OPD/ใบสั่งยา | `clinical-v3.js`, atomic prescription handoff | ยังไม่ใช่หลักฐานว่า telemedicine/video ทำงาน |
| นัดหมาย | `appointments.js`, appointment schema | มีการจองและยกเลิกนัดตามตาราง; ยังไม่มีการเชื่อมรับเงินก่อนปรึกษาหรือห้อง telemed |
| ห้องยา/จ่ายยา | `pharmacy.js`, prescription dispensing SQL | มี review และ FEFO; ยังไม่มีวงจร clarification ticket ครบตาม flow ใหม่ |
| ผลิต/QC/คลัง | `production.js`, `quality.js`, atomic production/QC SQL | มี production requests, batch, QC, finished-goods lots; ไม่ใช่ shipment/tracking |
| การเงิน | `app.js`, `record_atomic_invoice_payment` | เจ้าหน้าที่บันทึกแบบ manual หลังการจ่ายยา; ไม่ใช่ payment gateway ก่อน consult |
| Follow-up | `outcomes.js`, clinical follow-up schema | มีฐานข้อมูลติดตามผลทางคลินิก; ยังไม่ใช่ CRM automation/feedback lifecycle |
| AstroNeko → lead → booking | ไม่พบตัวเชื่อมเฉพาะใน audit รอบนี้ | ต้องสร้าง referral attribution, intake และการกันคิว |
| Online payment | ไม่พบ 2C2P/webhook/refund integration ใน audit รอบนี้ | ต้องสร้าง checkout, verified callback, reconciliation และ exception states |
| Telemed | ไม่พบ video/session integration ใน audit รอบนี้ | ต้องเลือกบริการและเชื่อมคิว/การยืนยันตัวตน/เวชระเบียน |
| Packing/shipping/CRM | ไม่พบ shipment/tracking/CRM integration ใน audit รอบนี้ | ต้องสร้างงานส่งมอบและติดตามต่อเนื่อง |

ผลทดสอบเดิม 10 เคสเป็น synthetic Practitioner → Pharmacy → Checkout ไม่ใช่การทดสอบเส้นทาง AstroNeko → gateway → telemed → ขนส่งจริง

## ลำดับงานต่อ

1. ปิด readiness gates เดิมของ core: authenticated roles, OFF/ON, LINE, backup/restore และ security/privacy/legal review
2. ทำ service order + referral + intake/booking + payment status ที่ตรวจสอบได้ แล้วเชื่อมการเปิด encounter เดิม
3. เชื่อม telemed และ pharmacy clarification/quote โดยรักษา revision ของใบสั่งยา
4. เชื่อม order ที่ชำระแล้วกับ existing stock/production/QC พร้อม packing/shipment
5. เชื่อม delivery → clinical follow-up/CRM โดยแยกสิทธิ์และวัตถุประสงค์ข้อมูล

ก่อน deploy แต่ละส่วน ต้องมีระบบจำลอง provider, ทดสอบด้วยข้อมูลสังเคราะห์บน staging และหลักฐานจากตัวเชื่อมจริงตามขอบเขตของส่วนนั้น

## ชุดทดสอบรับงานเป้าหมาย (ยังไม่รัน)

1. Lead → consult → สินค้ามีสต็อก → จัดส่ง → feedback
2. Lead → consult → ผลิตเฉพาะคำสั่ง → QC ผ่าน → ส่งมอบ
3. ไม่เหมาะกับทางไกล → ส่งต่อ/ยกเลิกตามนโยบาย โดยไม่สร้างคำสั่งยาอัตโนมัติ
4. ชำระล้มเหลว/หมดอายุ → ไม่ยืนยันคิวหรือผลิต และคืนคิวชั่วคราว
5. Payment callback ซ้ำ/สลับลำดับ → รับเงินและออกออร์เดอร์เพียงครั้งเดียว
6. ห้องยาส่งกลับแก้ใบสั่งยา → อนุมัติ revision/ราคาใหม่ก่อนเดินงาน
7. สต็อกไม่พอหรือ QC ไม่ผ่าน → ไม่ส่งสินค้าและมีงานแก้ไข/แจ้งลูกค้า
8. ที่อยู่ผิด ส่งไม่สำเร็จ คืนสินค้า/คืนเงิน → ติดตามและกระทบยอดได้
9. Feedback อาการผิดปกติ → เข้าคิวผู้ประกอบวิชาชีพ ไม่เข้าขายซ้ำอัตโนมัติ
10. ข้ามคลินิก/บัญชีไม่มีสิทธิ์/Owner OFF ระหว่าง flow → ปฏิเสธตามขอบเขต โดยไม่ทำงานซ้ำหลัง ON

## ต้นทุนที่ต้องเพิ่มจากรายงาน cloud

Flow นี้มีต้นทุนบริการต่อเคสเพิ่มจาก SaaS subscription: ค่าแรงผู้ประกอบวิชาชีพ, payment fee, ระบบสื่อสาร, วัตถุดิบและแรงผลิต, QC, บรรจุภัณฑ์, ขนส่ง, บริการลูกค้า/ติดตามผล, การตลาดที่จัดสรร, คืนเงิน/ส่งใหม่ และสัดส่วน cloud/AI ที่ใช้จริง

เงินเหลือก่อนค่าใช้จ่ายส่วนกลางต่อเคส = รายรับค่าปรึกษา + รายรับสินค้า − ค่าใช้จ่ายตรงทั้งหมดข้างต้น

ต้องแยกกำไรของบริการดูแลลูกค้าต่อเคสออกจากกำไรของแพ็กเกจ software ต่อคลินิก ห้ามใช้ราคา cloud เป็นตัวแทนต้นทุนธุรกิจทั้งหมด

## แหล่งอ้างอิงด้านขอบเขต telemedicine

[ประกาศสภาการแพทย์แผนไทย พ.ศ. 2564 เผยแพร่ราชกิจจานุเบกษา 8 ก.พ. 2565](https://infocenter.oic.go.th/FILEWEB/CABINFOCENTER20/DRAWER035/GENERAL/DATA0000/00000116.PDF) ระบุข้อจำกัดความเหมาะสมของการดูแลทางไกล การยืนยันผู้ให้/ผู้รับบริการ ความปลอดภัยระบบ และการดำเนินการผ่านสถานพยาบาล เอกสาร flow นี้ไม่ใช่ legal sign-off หรือการยืนยันว่าบริการเฉพาะของโครงการผ่านเงื่อนไขทั้งหมดแล้ว
